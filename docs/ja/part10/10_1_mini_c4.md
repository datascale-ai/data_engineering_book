# プロジェクト 1: Ray に基づいた分散 Mini-C4 データ パイプラインの構築

## 章の概要

P01 は、Common Crawl シャードから Mini-C4 トレーニング データ セットを構築するエンジニアリング プロセスに焦点を当てています。この章の焦点は、単一の結果のキャプチャではなく、Web ページのアーカイブ、テキストの抽出、重複排除とフィルタリング、トレーニングのパッケージ化、および結果の検証を再現可能なデータ生産ラインに編成することにあります。

この章は、次の 4 つの要点に従って理解できます。

- データ収集とテキスト抽出: トレーニングに使用できるテキストを Web アーカイブから抽出します。
- クリーニング、重複排除、品質管理: テンプレートのノイズ、重複に近いコンテンツ、混合言語、低品質のページに対処します。
- トレーニングのカプセル化とデータのセグメント化: 処理結果を標準化された JSONL およびトレーニング リストに整理します。
- 検証とコストの限界を評価する: スクリプト、統計メトリクス、リソース消費を検査することでパイプラインのステータスを評価します。

エンジニアリング順に読むと、この章は完全なリンクに相当します。

**Web ページのアーカイブ -> テキスト抽出 -> 基本クリーニング -> 準重複排除 -> 言語分割 -> 品質フィルタリング -> トレーニング パッケージ化 -> 評価と検証**

この構造に対応する中心的な目標は、単一の CPU と Ray の条件下で、解釈可能で再利用可能な Web ページの事前トレーニング データ パイプラインを再現することです。

---

## 1. プロジェクトの背景: Mini-C4 のエンジニアリング上の位置付け

大規模モデルの事前トレーニングでは、Web コーパスは常に最も重要なデータ ソースの 1 つです。 Web ページは十分に大きく、十分な範囲をカバーし、頻繁に更新されるため、一般的な事前トレーニング コーパスを構築するのに当然適しています。
しかし、Web データには次の 3 つの非常に典型的な問題もあります。

1. **非常に低い信号対雑音比**: HTML ページには、ナビゲーション バー、広告スペース、スクリプト、フッター、著作権記述、Cookie ヒント、コメント エリア、ディレクトリ ページなど、テキスト以外のコンテンツが多数含まれています。
2. **非常に高度な繰り返し**: 再版、ミラー サイト、集約ページ、テンプレート ページ、およびページの部分コピーが非常に頻繁に行われます。
3. **配布の制御が難しい**: さまざまな Web サイト、さまざまな言語、およびさまざまなテキスト品質が混在しているため、トレーニング コーパスがノイズ分布に向かって簡単に引っ張られる可能性があります。

したがって、トレーニング前のデータ エンジニアリングの核心は、「より多くのテキストを取得する」ことではなく、解釈可能、再現可能、検証可能なデータ生成パイプラインを確立して、元の Web ページをトレーニング システムに引き渡すことができるテキスト サンプルに徐々に収束させることです。

それが Mini-C4 のすべてです。これは完全な工業用グレードの C4 の代替品ではなく、**最小限の再現可能で実行可能で、明確に説明されたミニチュア バージョン**です。
これにより、単一シャードおよび単一 CPU の条件下での大規模な Web ページの事前トレーニング データ処理における主要な問題を完全に説明できるため、その後の大規模なデータ プロジェクトのための手法の基盤を築くことができます。

## 2. プロジェクトの目標と限界

### 2.1 プロジェクトの目標

このプロジェクトの目標は、単に Common Crawl データをダウンロードすることではなく、管理された境界内で次のリンクを完全に実行することです。

> **Web ページのアーカイブ -> テキスト抽出 -> 基本クリーニング -> 準重複排除 -> 言語分割 -> 品質フィルタリング -> トレーニング パッケージ化 -> 評価と検証**

最終的な出力には次のものが含まれます。

- `train.jsonl`
- `val.jsonl`
- `smoke_test.jsonl`
- `training_manifest.json`
- 評価報告書および検査報告書

このプロジェクトは、「Web ページをテキストに変換する」というステップに留まるのではなく、**Web ページをトレーニング データに変換する**ことに重点を置いています。

### 2.2 プロジェクトの境界

プロジェクトの再現性と制御性を最小限に抑えるために、このプロジェクトでは次の境界を明示的に設定します。

- **データ スケールの境界**: Common Crawl の 1 つのシャードのみを処理し、完全な産業規模は追求しません。
- **ハードウェア境界**: デフォルトでは、単一マシンの CPU 環境で実行され、GPU に依存しません。
- **並列境界**: 重複排除ステージでは、Ray を使用して単一マシンのマルチコア並列化を実行します。
- **言語境界**: 現在、主に英語と中国語をカバーしていますが、英語の品質フィルタリングはより完全であり、中国語の品質ゲートは比較的弱いです。
- **目標の位置付け境界**: これはエンジニアリングの実践を指向したケースであり、SOTA 指標を追求する研究プロジェクトではありません。

### 2.3 境界設定の役割

この境界設定には 2 つの利点があります。

まず、限られたリソースの下でもプロジェクトを確実に再現できます。
複数のマシン、大規模なシャーディング、および複雑なスケジューリングが最初から目標である場合、プロジェクトはすぐにインフラストラクチャの問題によって支配され、代わりにデータ エンジニアリング自体の重要なロジックが曖昧になります。

第 2 に、チームは各フィルタリング ステップの効果をより明確に観察できるようになります。
データが小さい場合、中間検査、手動サンプリング、およびしきい値調整を実行して、データが保持または削除される理由を正確に理解することが容易になります。

## 3. プロジェクトの全体構造

![图 1：Mini-C4 数据流水线总览](../../images/part10/10_1_fig01_mini_c4_pipeline_overview.png)



### 3.1 プロセスの概要

プロジェクトのプロセス全体は 10 のステップに要約できます。

1. `src/1_download_data.py`: 共通クロール データをダウンロードする
2. `src/2_process_warc.py`: WARC を解析してテキストを抽出する
3. `src/3_clean_data.py`: ヒューリスティック クリーニング
4. `src/4_deduplicate.py`: MinHash は重複を削除します
5. `src/5_split_lang.py`: 言語ごとに分割
6. `src/6_quality_filter.py`: 品質フィルタリング
7. `src/7_prepare_training_data.py`: トレーニング データのカプセル化
8. `src/8_evaluate_dataset.py`: データセットの評価
9. `src/9_training_smoke_test.py`: トレーニング煙テスト
10. `src/10_run_p1_checks.py`: プロジェクトの検査と一貫性の検証

### 3.2 3段階の理解方法

上記のプロセスをさらに分類すると、大きく次の 3 つの段階に分けることができます。

#### 第一段階：Webの世界からテキストの世界へ

この段階では主に「テキストがあるかどうか」という問題を解決します。主なタスクは次のとおりです。

- WARCをダウンロード
- Web ページの応答を読み取る
- HTML 以外のコンテンツをフィルタリングする
- HTMLから本文を抽出する

このステップの焦点は、Web アーカイブ内の複雑なコンテンツをできるだけ安定してテキストに変換することです。

#### 第二段階：テキストの世界からコーパスの世界へ

この段階では、主に次のような「テキストがコーパスとして使用できるかどうか」という問題が解決されます。

- 基本的な掃除
- 重複を削除する
- 言語の分裂
- 品質フィルタリング

つまり、ノイズ、繰り返し、分布を積極的に制御して、テキストをトレーニング コーパスの形状に近づけます。

#### 第 3 段階: コーパスの世界からトレーニング インターフェイスへ

この段階では、「コーパスをトレーニング システムに安定して供給できるかどうか」という次のような問題が解決されます。

- 決定的なトレイン/ヴァル分割
- マニフェストビルド
- スモークテストビルド
- 評価・検査

このステップが達成されて初めて、データ エンジニアリングが真にループを閉じることができます。

## 4. データ取得: 共通クロールのためのエンジニアリングの選択

Common Crawl は、Web ベースの事前トレーニング データセットを構築するために最も一般的に使用されるパブリック ソースの 1 つです。 Web スクレイピングの結果は WARC (Web ARCHive) 形式で保存され、HTTP 応答、ヘッダー情報、および元の Web コンテンツが保存されます。

Common Crawl を選択する主な理由は 3 つあります。

1. **大規模**: 多数の実際の Web ページのシナリオをカバーできます。
2. **形式の標準化**: WARC は、ストリーミング処理に適した成熟した Web アーカイブ形式です。
3. **実際の産業問題に近い**: Web ページのノイズ、テンプレート、重複、言語の混在などの問題がすべて発生します。

ただし、このため Common Crawl をトレーニングに直接使用することはできません。
厳密な抽出とフィルタリングを行わないと、モデルは大量の HTML フラグメント、著作権ページ、ディレクトリ ページ、テンプレートのジャンク テキストを学習します。

したがって、Common Crawl を選択すると、実際には実際の産業生産環境に近い一連の問題が選択されます。

## 5. WARC分析とテキスト抽出

### 5.1 最初のキーしきい値としてのテキスト抽出

Web ページは本来、自然言語テキストと同じではありません。 HTML ページには通常、次のものが混在しています。

- ナビゲーションバー
- パン粉
- 推奨位置
- JavaScript
- CSS
- フッターリンク
- 宣伝する
- 著作権に関する声明
- コメントエリア
- テーブルレイアウトのフラグメント

HTML を直接読んでタグを剥がすだけだと、モデルには一貫した意味論的なテキストではなく、大量の構造的断片が表示されることがよくあります。

したがって、テキスト抽出段階の目標は、「できるだけ多くの文字を取得する」ことではなく、メイン コンテンツ領域をできるだけ正確に抽出することです。

### 5.2 コアコンポーネントの選択

![图 2：WARC 到正文文本的解析路径](../../images/part10/10_1_fig02_warc_to_text.png)




|コンポーネント |選択 |選定理由 |
|---|---|---|
| WARC の読み取り | `warcio` |標準の WARC 読み取りライブラリは、一度に大きなファイルをロードすることによるメモリ負荷を回避するストリーミング処理をサポートします。
|テキスト抽出 | `trafilatura` |メインコンテンツ領域の抽出がより安定しました。単純な HTML 解析方法と比較して、ナビゲーション バー、フッター、テンプレート領域のクリーニング効果が高くなります。

### 5.3 ストリーミング処理の工学的価値

WARC ファイルはサイズが大きいことが多く、多数の不要な応答が含まれています。
ファイル全体を一度にメモリに読み込むとリソースが無駄になり、長時間のプロセスを安定して動作させることができません。

したがって、このプロジェクトでは **ストリーミング トラバーサル** を使用して WARC レコードを 1 つずつ読み取り、条件を満たす HTML 応答のみを処理し続けます。
この設計は、ピーク時のメモリ消費量を削減するだけでなく、複数のシャードに拡張する際のエンジニアリングの習慣により沿ったものになります。

### 5.4 コアの実装

```python
from warcio.archiveiterator import ArchiveIterator
import trafilatura

def extract_text_from_warc(warc_path, output_path):
    with open(warc_path, "rb") as stream:
        for record in ArchiveIterator(stream):
            if record.rec_type != "response":
                continue

            content_type = record.http_headers.get_header("Content-Type")
            if not content_type or "text/html" not in content_type:
                continue

            text = trafilatura.extract(
                record.content_stream().read(),
                include_comments=False,
                include_tables=False,
                no_fallback=False
            )
```

ここでのいくつかのパラメータは意図的なものです。

- `include_comments=False`: コメント領域などのノイズの多い領域を本文に含めないでください。
- `include_tables=False`: テーブルのレイアウトによって生じる構造的なノイズを軽減します。
- `no_fallback=False`: 再現率を向上させるために必要な場合に、抽出されたコンポーネントの修復抽出を許可します。

### 5.5 この段階での結果の意味

単一シャード テストでは、最終的に **3028** 個の候補テキストの抽出に成功しました。
この数字からわかることは 2 つあります。

まず、すべての Web ページの応答を使用可能なテキストに変換できるわけではありません。
第 2 に、テキスト抽出はすでに明らかなデータ圧縮です。これは、多数の元の応答が「非 HTML」、「空のコンテンツ」、「抽出失敗」およびその他のリンクでブロックされるためです。

エンジニアリングの観点から見ると、現段階での答えは次のとおりです。

> 実際のWebページのデータにおいて、「テキストっぽい」候補テキストをどれだけ安定して取得できるでしょうか？

## 6. ヒューリスティック クリーニング: 第一ラウンドのノイズ スクリーニング

![图 3：启发式清洗规则示意](../../images/part10/10_1_fig03_cleaning_rules.png)




### 6.1 ヒューリスティッククリーニングの必要性

たとえテキスト抽出が成功したとしても、結果として得られるテキストは高品質のコーパスとは程遠いものになります。
ページは「テキスト」を抽出している可能性がありますが、このテキストはまだ次のとおりである可能性があります。

- 非常に短いテキスト
- 目次ページ
- タグクラウド
- SEO スプライスされたテキスト
- コードスニペット
- システムエラーページ
- プライバシーと Cookie に関するヒント

このようなサンプルがトレーニング セットに直接送信されると、モデルが汚染されるだけでなく、その後のコンピューティング リソースも無駄になります。

したがって、通常、最も明白な低品質テキストを傍受するために、パイプライン内で安価で高速、解釈可能なヒューリスティック クリーニングの層が設計されます。

### 6.2 本プロジェクトで採用した主な清掃ルール

#### 1) 長さのルール

- 短すぎるテキストは破棄されます。 100文字未満
- 長すぎるテキスト (たとえば 200 万文字を超える) は破棄されます。

理由は非常に単純です。
短すぎるテキストには十分な意味情報が欠けていることがよくありますが、長すぎるテキストは異常な接合、ページの接合、または構造的な損傷の結果である可能性があります。

#### 2) 平均語長ルール

平均単語長が大幅に長い場合 (たとえば 15 文字を超える場合)、テキストは自然言語ではない可能性が高くなります。

- コード圧縮結果
- URL文字列
- 無差別識別子
- スタイルフラグメント

#### 3) シンボル密度ルール

次の記号の割合を数えます。

```text
{ } [ ] < > \
```

これらの記号が過剰に表現されると、テキストは自然言語の段落ではなく構造の断片に似ることがよくあります。

#### 4) ブラックリストフレーズルール

たとえばインターセプト:

- `lorem ipsum`
- `enable cookies`
- `403 forbidden`

これらのテキストはプレースホルダーまたはシステム プロンプト ページのいずれかであり、トレーニングにとって実際の価値はありません。

### 6.3 ヒューリスティッククリーニングの特徴

このルール層は「究極の精度」を追求するものではなく、最も明らかな問題を低コストで排除するものです。
その利点は次のとおりです。

- 速い
- 低コスト
- 説明が簡単
- パラメータの調整が簡単
- ファネルのフロントエンドとして最適

言い換えれば、この段階ではすべての品質問題を解決する責任はなく、「ほぼ確実に保管すべきではない」サンプルを除去することが優先されます。

### 6.4 この段階での結果の解釈

ヒューリスティック クリーニング後、サンプル数は **3028** から **2425** に減少しました。
これは、最も基本的なテキスト ルールの下では、候補テキストの約 5 分の 1 が低品質であると判断できることを示しています。

この段階の重要性は次のとおりです。

> 高価なモデルのスコアリングに依存せずに、最も粗いノイズが最初に抑制され、その後のより細かい処理のためのリソースが節約されます。

## 7. 重複除去：Webコーパスにおける重複に近い処理

![图 4：MinHash + LSH 去重思路](../../images/part10/10_1_fig04_dedup_minhash_lsh.png)



### 7.1 重複の問題はどの程度深刻ですか?

インターネットのテキストには、以下を含むがこれらに限定されない大量の重複があります。

- 転載記事
- 集計ページ
- ミラーサイト
- テンプレートページ
- ページが部分的に重なっている
- 同じコンテンツの異なるレイアウト バージョン

重複が削除されない場合、トレーニング コーパスでいくつかの問題が発生します。

1. 一部のコンテンツが過度に繰り返され、不均衡な配信が発生します。
2. モデルは、特定のテンプレートまたはサイトに対して強力なメモリを持っている可能性があります。
3. その後の評価中にデータ漏洩が発生する可能性があります。
4. 重複したコンテンツによって、ストレージとトレーニングのリソースが不必要に消費されます。

したがって、重複排除はおまけではなく、Web の事前トレーニング データ エンジニアリングにおいて必要なステップです。

### 7.2 ペアごとの比較を避ける理由

\(N\) 個のテキストがあると仮定して、ペアごとの類似度を直接比較すると、複雑さは \(O(N^2)\) に近くなります。
実際のデータ規模では、このアプローチはすぐに受け入れられなくなります。

そこで、このプロジェクトでは、**MinHash + LSH** という考え方を採用し、「類似するテキストを見つける」という問題を「類似する署名を見つける」という問題に変換し、処理の複雑さをより実装可能な範囲まで軽減します。

### 7.3 MinHash と LSH のエンジニアリングの直観

- **MinHash**: テキストの一部を短い署名にマッピングします。署名は、テキストの設定された類似性をほぼ反映します。
- **LSH (ローカル機密ハッシュ)**: 類似したテキストが同じ候補バケットに分類される可能性が高くなり、グローバル比較の数が減ります。

この結果、各テキストをすべてのテキストと比較する必要はなくなり、類似する可能性がより高い候補セットの中でのみ決定を下すようになります。

### 7.4 Ray を使用する場合のエンジニアリング上の考慮事項

MinHash を使用しても、署名自体の生成は依然として計算量の多い操作です。
特にテキスト項目の数が増えると、シングルスレッド処理ではパイプライン全体の速度が大幅に低下します。

ここでのレイの役割は非常に明確です。
これは見せびらかすための「分散」ではなく、単一のマルチコア CPU でバッチ処理タスクを並列実行できるようにするためのものです。

対応する実装は次のとおりです。

```python
import ray
from datasketch import MinHash

@ray.remote
def process_batch(lines, batch_id):
    results = []
    for line in lines:
        item = json.loads(line)
        m = MinHash(num_perm=128)
        for w in item["text"].split():
            m.update(w.encode("utf8"))
        results.append((item["url"], m, item["text"]))
    return results

futures = [process_batch.remote(batch, i) for i, batch in enumerate(batches)]
processed_batches = ray.get(futures)
```

### 7.5 ここでの最も簡単な落とし穴

Ray 並列処理に関する最も一般的な誤解の 1 つは次のとおりです。
**単一のテキストを独立したタスクとしてディスパッチしないでください。 **

これにより、小さなオブジェクトのシリアル化とプロセス間通信のオーバーヘッドが大量に発生し、最終的にパフォーマンスが低下します。
正しい方法は次のとおりです。

- まずテキストをバッチにパッケージ化します
- 次にバッチを押してワーカーにディスパッチします

たとえば、1,000 アイテムごとにバッチ処理する方が、エンジニアリング的にはより安全な選択です。

### 7.6 この段階での結果の解釈

重複排除後、サンプル数は **2425** から **2305** に減少しました。
これは、重複の問題は存在しますが、この最小限の実験規模では、重複排除によって引き起こされる縮小がマス フィルタリングほど深刻ではないことを示しています。

しかし、これは重複排除が重要ではないという意味ではありません。
それどころか、重複排除の重要性は、アイテムの数を減らすだけでなく、トレーニング配布の健全性を大幅に改善できることです。

## 8. 言語分割: 言語ごとの処理の必要性

![图 5：语种拆分与分支处理](../../images/part10/10_1_fig05_language_split.png)

### 8.1 異なる言語は同じ品質ゲートのセットを共有できない

Web ページのテキストの品質の判断は、言語自体に大きく依存します。
たとえば、英語の一部の混乱しきい値、単語の長さの統計、文法的自然さの規則は中国語には適用されません。
逆に、中国語の Web ページでよくある問題は、英語の Web ページで発生する問題とまったく同じではありません。

したがって、プロジェクトは重複排除後、すべての言語を同じフィルターに入れるのではなく、品質管理をより正確にするために言語ごとにテキストをさらに分割しました。

### 8.2 このプロジェクトのアプローチ

このプロジェクトは、FastText の言語認識モデル `lid.176.ftz` を使用してテキストの言語を予測し、テキストを次のように分割します。

- `en`
- `zh`
- `others`

これを行った後、後続の品質フィルタリングでは言語に応じて異なる戦略を使用できます。

### 8.3 必要な中間層としての言語分割

言語分割の価値は主に次の 3 つの側面に反映されます。

1. **誤った判断を避ける**: 言語ごとにテキストの統計的特徴は大きく異なります。
2. **分析の容易さ**: 保持率とブロックの理由を言語ごとに個別に観察できます。
3. **拡張が簡単**: 将来さらに多くの言語が追加された場合、車輪を再発明することなく、このレイヤーに言語ブランチを追加するだけで済みます。

エンジニアリング組織の観点から見ると、言語分割によりパイプラインが「統合処理」から「プラガブル処理」にアップグレードされます。

## 9. 品質フィルタリング：「テキストっぽい」から「トレーニングに適した」まで

![图 6：质量过滤决策示意](../../images/part10/10_1_fig06_quality_filter.png)

### 9.1 なぜ品質フィルタリングが最も重要なドアなのか

ヒューリスティック クリーニングと重複排除は多くの明示的な問題を解決しますが、それでもテキストがトレーニングに本当に適しているかどうかを保証することはできません。
多くのページはテキスト ルールに準拠しているように見えますが、実際には次のとおりである可能性があるためです。

- 目次ページ
- 情報密度の低いページ
- 繰り返される文の積み重ねられたページ
- 言語の壊れたページ
- 機械翻訳の断片
- 文法的な自然性に乏しい Web ページのノイズ

このとき、より「言語品質」に近いフィルタリングのレイヤーが必要になります。

### 9.2 英語品質ゲート: KenLM Perplexity

このプロジェクトでは、品質フィルタリングのために英語側に KenLM 言語モデルを導入します。
核となるアイデアは次のとおりです。

- 言語モデルを使用してテキストをスコアリングする
- 単位あたりの単語数で正規化されたスコアを使用してテキストの自然さを測定します
- 明らかに不自然なテキストを閾値処理によって除外する

これは経験的に次のように理解できます。

- `> -5.0`: 通常は高品質のテキストに近い
- `< -6.0`: 壊れた文、意味不明な出力、または低品質の出力に近づく傾向があります

これは、混乱度が低いほど優れているという意味ではなく、言語モデルが純粋なルールよりも「自然言語の品質」に近い信号として機能する可能性があるということです。

### 9.3 このプロジェクトで観察された傍受の主な理由

品質フィルタリング段階では、ブロックされる一般的な理由は次のとおりです。

- `directory_like`: ディレクトリ Web ページ、情報密度が低い
- `duplicate_lines`: ページ内に重複行が多すぎます
- `too_few_tokens`: 有効なトークンが少なすぎます

これらのルールは KenLM とともに、「ヒューリスティック + 言語の自然さ」の共同フィルタリング戦略を形成します。

### 9.4 中国語と英語の定着率の違いは何を示していますか?

最終結果は次のようになります。

- 英語候補セット **846**、**502** 予約済み
- 中国候補者セット **201**、**24** 予約済み

この違いは非常に代表的なものです。
これは単に「不十分な中国データ」を説明するだけでなく、より現実的な 2 つの問題を明らかにしています。

1. 現在の中国語の品質フィルタリング機能は、英語のものよりも大幅に弱いです。
2. 中国語の Web ページの構造やノイズ パターンは英語の Web ページとは異なる場合があり、英語のルールをそのまま適用することはできません。

これは、産業レベルの多言語データ エンジニアリングにおいて、よりきめ細かいローカリゼーションを考慮して言語品質モデルを設計する必要があることも意味します。

プロジェクトを一連のスクリプト呼び出しとしてのみ理解している場合、これらの設計の背後にあるトレードオフを明確に理解するのは簡単ではありません。

したがって、1ラウンド目の答えは「テキストはありますか？」です。 「これらのテキストはトレーニングできますか?」ではなく、

### 10.2 実験 2: ヒューリスティック クリーニングと重複排除の追加

第2回目からは「テキストの抽出」から「コーパス化の予備化」へとプロジェクトがグレードアップしました。

## 11. トレーニング データのカプセル化: クリーニング結果からトレーニング インターフェイスまで

### 11.1 データクリーニングはトレーニングが利用可能であることを意味するものではありません

最終的に保存されたテキストが比較的きれいだったとしても、それはまだ「トレーニングの準備ができている」とは直接言えません。
通常、トレーニング システムには次の機能も必要となるためです。

- 安定したトレイン/ヴァル分割
- メタデータインデックス
- トークンの見積もり
- 少量サンプルの煙テスト
- ファイルレベルの構成

このステップが適切に行われていない場合、その後のトレーニングと評価で不一致や漏れの問題が簡単に発生する可能性があります。

### 11.2 決定論的セグメンテーションの重要性

プロジェクトはランダムに分割されるのではなく、`text_sha1` などの決定的な識別子に基づいて分割されます。
これを行うことの利点は次のとおりです。

- 繰り返し実行すると、train/val セットは安定し、変化しません。
- トレーニング結果の差異のトラブルシューティングを容易にします
- データセットのバージョン管理に便利
- プロジェクトの再現性に貢献

ここで強調する必要があるのは次のことです。
**再現性はデータ エンジニアリングの品質の一部であり、アドオンではありません。 **

### 11.3 発煙試験の機能

プロジェクトはさらに `smoke_test.jsonl` をビルドします。
これは正式なトレーニング セットの一部ではありませんが、非常に小さく、高速に読み込まれるサンプル コレクションであり、次の用途に使用されます。

- トレーニング スクリプトを実行する
- トークナイザーとデータインターフェースが正常かどうかを確認してください
- 書式設定エラー、エンコードの問題、またはフィールドの欠落を早期に検出します

実際のプロジェクトでは、このスモーク テスト セットにより、多くの場合、デバッグ時間を大幅に節約できます。

### 11.4 マニフェストの工学的価値

`training_manifest.json` は、次のようなデータ セットの重要なメタ情報を記録します。

- サンプルサイズ
- セグメンテーションの状況
- トークンの数を見積もる
- ファイルパス
- 重複チェック結果

その重要性は、データ セットを単なるいくつかの散在する JSONL ファイルではなく、システムによって読み取り、評価、検査できる「正式な製品」にすることです。

## 15. 主な制限事項とリスク

最小限の再現可能なプロジェクトは決して最終的なものではありません。
Mini-C4 の価値はメソッドを説明することにありますが、非常に明確な制限もあります。

### 15.1 低い定着率

最終的な定着率はわずか **17.37%** でした。
これは、Web ページの元のノイズが実際に非常に大きいことを示しており、また、現在の品質ゲートが比較的厳しいことも示しています。

これは悪いことではありませんが、目標が「スケールの最大化」に移行した場合、有効な可能性のあるデータが大量に一括で削除されることを避けるために、ルールとモデルをさらに最適化する必要があることを意味します。

### 15.2 中国人の定着率が低い

最終的に、中国語で保持された項目は **24** のみであり、中国語の品質スコアリング能力が不十分であるという問題が明らかになりました。
しきい値を調整するだけでは完全に解決できませんが、次のことが必要になる場合があります。

- 中国のウェブページのデータ品質ルールにさらに適合
- 中国語により適した言語モデルまたはスコアリングモデル
- 中国の Web ページサンプルのより詳細な分析

### 15.3 重複排除のスケーラビリティには限界がある

現在でも、メモリのインデックス作成が重複排除の主な方法です。
シャードの数が増えると、最初に次のような問題が発生します。

- 記憶のプレッシャー
- 実行時間が増加する
- グローバルインデックス管理は難しい

したがって、現在のソリューションは、非常に大規模な運用環境に直接移行するよりも、最小限の実験や中小規模のデータ処理に適しています。

## 16. フォローアップ展開の方向性

### 16.1 重複排除バックエンドのアップグレード

現在のメモリ内 LSH インデックスを外部ストレージにアップグレードします。例:

- レディス
- カサンドラ
- その他の分散型 KV/インデックス システム

これにより、より多くのシャードの重複排除要件をサポートできます。

### 16.2 中国品質モデルのアップグレード

次のような、中国語の Web ページ データのより安定した品質モデリング方法を導入します。

- より適切な中国語モデル
- 中国の Web ページの品質特徴エンジニアリング
- 軽量で高品質な分類器

### 16.3 プレフィックスドメイン名のフィルタリング

HTML 解析の前にドメイン レベルのホワイトリスト/ブラックリスト フィルタリングを実行すると、その後の無効な計算を大幅に減らすことができます。
これは「テキスト側のクリーニング」から「クローリング入力制御」への重要なステップです。

### 16.4 可観測性の向上

各ステージに以下を追加します。

- 時間のかかるログ
- スループット統計
- サンプル検査パネル
- しきい値ヒット統計

このようにして、開発者はパラメータを調整するときに「結果が変わった」だけでなく「なぜ変わったのか」も知ることができます。

## 17. エンジニアリング実践の要約: Mini-C4 メソッドの価値

![图 11：Mini-C4 工程方法论总结](../../images/part10/10_1_fig11_methodology_summary.png)

このプロジェクトが本当に伝えたいのは、特定のライブラリの使用法ではなく、より一般的なデータ エンジニアリング方法論です。

1. **最初に、制御可能な境界内のリンク全体を実行します**
2. **各ステップを説明可能な段階にします**
3. **結果検証の閉ループを確立することが優先されます**
4. **ファネルと中間メトリクスを通じてシステムの動作を観察します**
5. **規模を拡大する前に、アプローチが有効であることを確認してください**

Mini-C4 の価値は、1 つのシャードのみを処理するということではなく、Web 事前トレーニング データ エンジニアリングの中核となる問題を再現可能なパイプラインに凝縮していることです。

この組立ラインには、完全なエンジニアリング閉ループに必要ないくつかの要素も含まれています。

- 明確な目標を持つ
- 完全なプロセスがあります
- 本物の指標がある
- 選択できる中間点があります
- 制限と拡張があります
- エンジニアリングの閉ループが存在する

## 19. 結論

大規模なモデルのトレーニングの場合、多くの場合、データはモデルよりも「クリーンアップ」するのが困難です。
モデル アーキテクチャは再利用でき、トレーニング フレームワークは移行できるため、高品質のコーパス作成は常に堅固なデータ エンジニアリング機能に依存します。

Mini-C4 のケースは、次のことを証明しています。
非常に限られた境界の下でも、トレーニング前のデータ エンジニアリングにおける重要な問題を明確かつ完全に説明し、それらを再利用可能な方法論にまとめることはできます。

これは、このタイプのエンジニアリング パイプラインの再利用性の中核でもあります。

## 特別トピック: Mini-C4 パイプラインの受け入れベースライン

Mini-C4 のようなプロジェクトは、「Common Crawl の小型版」と誤解されやすいです。しかし、エンジニアリングの観点から見ると、本当に再利用する価値があるのは、トレーニング前のデータ処理が許容可能なステージ チェーンに書き込まれることです。いわゆる承認は、`final_data.jsonl` の最終出力で終了することを意味するのではなく、各層が「引き続きダウンする必要がある」かどうかを決定できるベースラインを持たなければならないことを意味します。

### 1. ベースラインのキャプチャと解析

クロールと解析の最初の段階で最も重要なことは、さらに何ページをキャプチャするかではなく、キャプチャしたページを安定して解析できるかどうかです。少なくとも注意すべき点がいくつかあります。

* WARC サンプルを正しく展開できるかどうか。
* HTML 解析後に広告やナビゲーション ノイズの代わりにメイン コンテンツを保持するかどうか。
* URL、言語、本文の長さ、メタ情報など、解析フィールドが完全かどうか。
* 解析に失敗したサンプルを静かに破棄するのではなくログに記録するかどうか。

このステップの価値は、「原料層の問題」をできるだけ早く明らかにすることです。原材料レイヤーがひどく歪んでいる場合、その後のクリーニング、重複排除、スコアリングでは、ノイズに関してより高価な計算が実行され続ける可能性が高いためです。

### 2. クリーニングと重複排除のベースライン

クリーニングと重複排除の段階は、チームが「指標は強そうに見えるが、何がクリーニングされたのかわからない」という罠に最も陥りやすい時期です。より賢明なアプローチは、定量的指標とサンプル検査の両方を保持することです。

このレベルのより重要なベースラインには次のものがあります。

* クリーニング後もテキストの長さの分布は適切ですか?
* テンプレート ページ、ナビゲーション ページ、およびスクリプトの残りのページが大幅に減少したかどうか。
* 重複排除後も十分なトピックの多様性が維持されているかどうか。
* 異なるシャード間の重複が効果的に処理されるかどうか。
* 価値の高い長文はルールによってあまり害を受けないのでしょうか?

学習前コーパスの場合、重複を削除することの難しさは単に「繰り返しがあるかどうか」ではなく、「重複を削除した後に何が残るか」です。最終的に同じような構造の短いページだけになる場合は、維持率が良好に見えても、トレーニングの価値は高くない可能性があります。

### 3. 言語のセグメンテーションと品質スコアのベースライン

Mini-C4 は現在、英語と中国語を別々に処理します。言語が異なれば、Web ページの構造、ノイズの種類、信号の品質が大きく異なるため、このステップは非常に重要です。言語のセグメンテーション後は、品質スコアリングは統一されたしきい値だけを調べるのではなく、言語の特徴と組み合わせる必要があります。

このレベルでは、より重要なベースラインには次のものがあります。

* 中国語と英語が混在するページの誤分類を避けるために言語認識が安定しているかどうか。
* 各言語の保持率がサンプル品質の直感と一致しているかどうか。
* 品質のしきい値を変更した後、保持されるコーパスのトピックと長さの分布は大幅に変動しますか?
* 最終的に保持されたコーパスには、低価値サイトの明らかなクラスターがまだ存在しますか?

これらのベースラインを総合すると、残りのコーパスが「よりきれい」であるか、単に「少ない」かという 1 つのことが決まります。エンジニアリングにおいて、この 2 つは同じものではありません。

## 特別トピック: プロトタイプの指導から大規模な事前トレーニング工場まで

P01 の現在の形式は、最小閉ループの教育としてより適していますが、将来の大規模工場へのいくつかの重要な道筋を明確に示しています。ここで強調すべき最も重要なことは、スケールアップは単に「より多くのマシンでスクリプトを実行する」ということだけでは理解できず、コントロール サーフェス、可観測性、およびエラー処理機能も同時に拡張する必要があるということです。

### 1. まずコントロールサーフェスを拡張し、次にデータボリュームを拡張します

多くのチームは最初からデータ量を拡大したいと考えていますが、コントロール サーフェスが弱すぎると、規模が大きくなるほど問題を特定するのが難しくなります。通常、より合理的な順序は次のとおりです。

* まず、ステージレベルのログと統計を完了します。
* 次に、サンプルのサンプリングとルールのヒット分布を完了します。
* 次に、シャード数と並列処理を拡張します。
* 最後に、より高いスループットとより広いカバレッジを追求します。

コントロールサーフェスが十分に強力である場合にのみ、チームは問題がどこにあるのか、なぜ問題が発生するのか、規模が拡大したときにどのセクションを最初に修理する必要があるのか​​を知ることができるからです。

### 2. 学習前のコーパスファクトリーには「入力管理」が必要

P01 プレフィックス付きドメイン名のフィルタリングについてはすでに説明しましたが、これは実際には非常に重要です。なぜなら、事前トレーニング データのコストの多くは、価値の高いコンテンツには費やされず、大量の価値の低いページのダウンロード、解析、クリーニング、重複排除に費やされるからです。今後、より現実的な工場形態に移行しようとすると、以下のような入退室管理がますます重要になります。

* ドメイン名のホワイトリストとブラックリスト。
* サイト品質のポートレート。
* 更新頻度とクロール優先度。
* さまざまな言語や地域のサイトの差別化戦略。

注入口の管理が十分に行われていれば、その後の洗浄圧力と計算コストは​​大幅に削減されます。

### 3. 事前トレーニングプロジェクトの最後の競争は、持続可能な生産能力です。

長期的には、トレーニング前コーパス プロジェクトの本当の競争は、特定の時点でデータがどれだけ美しく洗浄されるかではなく、次のバージョンのコーパスを継続的、安定的、再現可能に生成できるかどうかです。これを行うには、少なくとも次のものが必要です。

* 明確なバージョンがあります。
* ステージのベースラインがあります。
* 異常なサンプルは保持されます。
* 品質変化の原因については説明があります。
* トレーニング側で使用できる安定したインターフェイスがあります。

これは、Mini-C4 がプロジェクトのプロトタイプとして最も価値があるところです。それは完全な産業システムであるかのように装っているわけではありませんが、産業システムの最も重要な骨格を最初に示しています。将来的にチームがどれだけ拡大しても、採用言語が増えても、新しいルールがどれだけ追加されても、この骨格が残っている限り、手法は成長し続ける余地があります。

## 特別トピック: コーパス比率とトレーニング混合戦略に関する予備的な考え

Mini-C4 のこの章はデータ クリーニングと品質管理に焦点を当てていますが、事前トレーニング プロジェクトの全体的な観点からは、コーパス率も事前に検討する価値のある問題です。なぜなら、「クリーニング」はそれが使用できるかどうかの問題を解決するだけであり、「どのように混合するか」は、トレーニングに入った後にこれらのコーパスが配布にどのような影響を与えるかを決定するからです。

### 1. 混合に必要な情報は、データ準備段階で保持される必要があります。

チームが後で言語、ソース、長さ、または品質によって階層化されたデータを混合する予定の場合、トレーニング前に再推測するのではなく、データ準備段階で関連するフィールドを保持する必要があります。保持できる最も一般的な情報には次のものがあります。

* 言語タグ。
* ソースドメイン名またはソースタイプ。
* テキストの長さの間隔。
* 質量分率または質量バケット。
* 重複排除の前後の状態。

これらのフィールドは、現在の最小限のプロジェクトでは「後で説明する」ように見えるかもしれませんが、プロポーションのトレーニング段階に入ると、すぐに最も価値のあるコントロール ハンドルになります。

### 2. トレーニングのハイブリッド戦略は本質的に品質管理の継続です

多くの人は、クリーニングをデータ エンジニアリング、ミキシングをトレーニング エンジニアリングとみなしていますが、トレーニング前のプロジェクトでは、この 2 つは実際には連続したチェーンです。高品質の長いテキストがクリーニング後も保持されているが、トレーニング混合中に過度に薄められた場合、以前のクリーニングの利点を実際にモデルに移すことが困難になるためです。一方、特定の種類の低品質だが頻度の高い Web ページが大量に保持され、トレーニングで過度に高い割合を占める場合、依然としてモデルは大きく乱れます。

この観点から、Mini-C4 が現在保持している構造化フィールドと中間生成物は、クリーニング プロセスに役立つだけでなく、その後のより洗練されたトレーニング ハイブリッド戦略のためのインターフェイスも確保しています。
